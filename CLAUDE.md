# Fart Raft

A browser clone of [Fart Together](https://store.steampowered.com/app/5117550/Fart_Together/): 2–4 players sit on one raft, and each player's farts push it at their seat. Off-center pushes turn the raft. The skill is coordination. Get through obstacle courses with checkpoints against the clock.

Plan: **single player / couch co-op first, online multiplayer later.** Every architecture rule below exists so multiplayer becomes a swap of input sources, not a rewrite.

## Commands

```bash
pnpm dev        # vp dev → http://localhost:5173
pnpm start      # vp build, then the server also serves dist/ (STATIC=dist): one URL for game + /rpc
pnpm share      # public https://*.trycloudflare.com tunnel to localhost:$PORT (default 3000), no account needed
pnpm dev:server # online server: node server/main.ts → ws://localhost:3000/rpc (PORT=… to change). Not `pnpm server`: pnpm reserves that name
pnpm check      # vp check (fmt + lint + type-aware typecheck) + sim-only tsc + server tsc + vp test run
pnpm build      # vp build
pnpm fmt        # vp fmt
pnpm blender    # open assets-src/fart-raft.blend with the MCP server auto-started (localhost:9876)
pnpm kit        # headless Blender: build_kit.py → export_kit.py → public/models/kit.glb
pnpm course     # scripts/canyon.ts → courses/canyon.json (the course the client plays)
pnpm graveyard  # scripts/graveyard.ts → courses/graveyard.json (wide pools, octagon islands, logs and bumpers)
```

Toolchain is **Vite+** (`vite-plus`, `vp`): lint/fmt/test config all live in `vite.config.ts`. Import test APIs from `vite-plus/test`, not `vitest` (enforced by `vite-plus/prefer-vite-plus-imports`). The pre-commit hook runs `vp staged`.

## Stack

- **Three.js** renders 3D. **Rapier 2D** (`@dimforge/rapier2d-compat`) simulates on the water plane. 2D physics, 3D visuals.
- **Blender** (+ Blender MCP) for models and course layout, exported to `.glb` + `.json`.
- **Effect v4** (`effect`, `@effect/platform-node`) for the online server and the RPC client. Effect lives only in `server/` and `src/net/` (lint blocks it in `src/sim`, `src/client`, `src/input`).

## Architecture

```
 Keyboard / Gamepad / Bot / Network        Blender
          │ SeatInput (Command)              │ course .json (LevelData) + .glb (visuals)
          ▼                                  ▼
 ┌──────────── src/sim/ (pure TS: no DOM, no Three) ────────────┐
 │ step(sim, inputs[]) → SimEvent[]   fixed 60 Hz               │
 │ raft + gas · hazards.update() · phase state machine          │
 └──────┬─────────────────────────────────────────┬─────────────┘
        │ snapshot(sim) → Snapshot (prev/curr)    │ SimEvent[]
        ▼                                         ▼
  client/render interpolates          client/fx + ui: particles, shake, HUD (later audio)
```

### The three rules

1. **Inputs are data.** The sim only sees `SeatInput { move, fart }` per seat per tick (`move` is a world-space stick vector). It never reads the keyboard or the camera.
2. **Fixed timestep.** The sim steps at 60 Hz (`STEP`), rendering interpolates with `alpha`. Never pass a variable `dt` into the sim.
3. **`src/sim/` is headless.** It must run unchanged in Node (tests prove it today, the server later).

Online play is the same sim behind a different `InputSource`: the server runs `src/sim` unchanged, clients send `SeatInput` over Effect RPC and receive `Frame { snapshot, events }` at 20 Hz. RPCs: `CreateRoom { course, difficulty, mode }` → 4-letter code (the room races every race at that difficulty; `Roster.difficulty` and `Snapshot.difficulty` carry it), `Join { code, name, look }` stream (= the seat lease: `Welcome { seat, token }`, then `Roster` on every change, then frames once started), `SendInput` / `Start` (host only) / `Restart` (any seated player) / `SetLook` (your own look, lobby or mid-race) / `SetTeam { team }` (your own team for the next race, lobby or mid-race) / `SetMode { mode }` (host only, applies to the next race), each carrying `{ code, token }`, so a client can only steer its own seat. **Team rooms:** `RoomMode = "coop" | "ghost" | "bump"` (`MODES`); the sim only sees `contactOf(mode)` (bump collides, the rest ghost). `Team = 0 | 1` (`TEAMS` = Red, Blue; a team's number is its raft's index in `Snapshot.crews`), at most `MAX_TEAM` = 4 each, so a room of `MAX_CREW` = 8 splits into two full teams. Every player has a team, co-op rooms included (they ignore it), so switching a room to a team mode finds it already split: `Join` takes the team with fewer players (Red on a tie), `SetTeam` is ignored when the target team is full, and players keep their team across mode switches. A team race's `Start` and `Restart` build `createSim(level, [crewZones(red), crewZones(blue)], { difficulty, contact })` with the inputs flat, Red's riders then Blue's, and both are ignored while a team has nobody on it (`startBlocker(roster)` = "Both teams need a rider", for the lobby to show next to Start). The race keeps the crews it started with: `SetTeam` and `SetMode` mid-race change the roster at once and the race from the next `Restart`, which keeps the room's mode and the teams as they are then. **No bots online:** Start and Restart make the race's crew exactly the humans seated at that moment, in seat order (per team in a team room), so `crewZones(n)` with n = humans on that raft, up to `MAX_CREW` = 8 per room (a ninth `Join` fails with `RoomFull`). A player's rider can differ from their lobby seat: `Roster.mode`, `Roster.seats[i] = { name, look, team } | null` and `Roster.crew[i] = { name, seat, look, raft }` (the sim's flat rider order: raft 0's riders, then raft 1's) say who sits where and who drives which rider (`placeOf(roster, seat)` = `{ raft, rider }`, the rider index within its raft as in `fart.seat`, null = spectating). A mid-race joiner is seated but only watches (banner, input ignored) until the next restart; a leaver's rider stays on the raft idle (`seat: null`) until then. The client reads the crew size from its `View`'s `riders.length` each frame, so the scene's zone marks, riders and name tags follow a crew change on restart without a reload. Relative imports carry explicit `.ts` extensions (Node strips types but does not resolve extensionless paths); `import/extensions` enforces it.

Rule 3 is enforced by tooling, not just this doc:

- `tsconfig.sim.json` type-checks `src/sim` with no DOM lib → `document`/`window` fail to compile.
- The lint override in `vite.config.ts` blocks `three` and `client/`, `input/`, `net/` imports from `src/sim/**`, and `client/` imports from `src/input/**`.
- `sim.test.ts` asserts determinism (same inputs → identical snapshot) and headless runs.
- `src/net/protocol.ts` ends with a `Drift` type that fails the typecheck when its schemas and `src/sim/types.ts` stop matching.

### Game programming patterns in use (Nystrom)

| Pattern             | Where                                                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------------------- |
| Game Loop           | `client/loop.ts`: fixed step, max 5 steps/frame, 250 ms clamp, interpolation, returns `stop()`        |
| Command             | `SeatInput`, `input/sources.ts` (`InputSource`, `idleSource` null object)                             |
| Update Method       | `sim/hazards/*`: each hazard has `update(dt)`                                                         |
| State               | `sim/flow.ts`: `countdown → racing → finished` as union + switch                                      |
| State (app)         | `client/app.ts`: `menu → online → room → racing` as union + switch; each state owns its DOM/listeners |
| Event Queue         | `step()` returns `SimEvent[]`; `client/race.ts` drains them once per frame into its `EventSink[]`     |
| Type Object (light) | `sim/hazards/index.ts` `KINDS`: data picks `kind` + tuning, one `<kind>.ts` owns behavior             |

**Deliberately not used** (add only when the problem shows up, measure first): Component/ECS (too few entity types), Singleton/Service Locator (pass deps explicitly), Spatial Partition (Rapier's broadphase), Object Pool (particles use a fixed `InstancedMesh` ring instead).

## Conventions

- **Coordinates:** sim is 2D, `+x` = raft forward, `+y` = left. Three is Y-up: sim `(x, y)` → three `(x, 0, -y)`, sim `rot` → `rotation.y`. All conversion goes through `client/render/coords.ts`.
- **Zones:** the raft is round (`RAFT_RADIUS`). Riders wade in the water around it (`RIDER_RING`), hands on the ring, always facing its center: butt out. A crew of n (1–`MAX_CREW` = 8) splits the ring into n equal arcs: `createSim(level, crewZones(n))` (1 = whole ring, 2 = left/right halves, 3 = thirds, 4 = quarters: `0` rear-left, `1` rear-right, `2` front-left, `3` front-right). 5–8 come from `ring(n)` in the same order: mirrored left/right pairs from the rear forward, even seats on the left, an odd crew's last seat dead ahead. Every crew rides the same raft: a bigger one for big crews could not pass the courses' gaps, and eight bodies still fit, each with ±10° of arc to slide. The stick slides a rider along its arc (`clampToZone`); a fart is a short burst (`FART_TICKS`, `FART_COOLDOWN`, `FART_COST`) that pushes the raft from the rider toward the center, so position is the only steering and the raft never spins from farts. The collider (`RAFT_HULL`) includes the riders. Rider poses are in `Crew.riders`. The client tints each arc in its seat color (`client/render/zones.ts`, 8 `SEAT_COLORS`). Each rider pushes `crewPower(n)` × `FART_FORCE`: 2 alone, 1 for 2–4, `(4/n)^(2/3)` beyond, so the strongest push a big crew can aim one way matches a crew of four's (`sim.test.ts` checks 5–8 within 85–105%).
- **Rafts and views:** one Rapier world holds every raft in a race: `createSim(level, crews, { contact })` takes one zone layout per raft (co-op is `[crewZones(n)]`, one raft) and `step()` takes their inputs flat, raft 0's riders first. Hazards are shared bodies, so every raft meets the same hazard on the same tick. `Snapshot` is the whole race (`tick`, `difficulty`, `contact`, `hazards`, `crews: Crew[]`, one per raft); `viewOf(snapshot, raft)` (`sim/view.ts`) gives one raft's `View` (its `Crew` at the top level plus `rivals`), which every client and bot consumer reads; `client/session.ts` is the boundary: it picks the raft the camera follows and splits events into felt and seen ones (see Team race client). Every raft event carries `raft`. `contact` is `"ghost"` (default: rafts never touch, Rapier collision groups) or `"bump"`: rafts collide (`bump` event with `rival: true`, never a wipeout), a fart shoves a rival hull within `RIVAL_REACH` of the rider at `RIVAL_BLAST` of the own push, and a raft in its respawn grace passes through rivals until it is clear of them. Rafts start side by side across the spawn, `TEAM_SPACING` apart (raft 0 on the left), and respawn in the same lanes at their gate; in Bump a lane on top of a rival moves upstream until clear. `winnerOf(crews)` is the first finisher, `"draw"` on the same tick, null before.
- **Online lobby** (`client/ui/lobby.ts`): Play online → name, then join by code or create a game on a course. The room screen shows the big code, a copy/share invite link (`?room=CODE`, plus `&server=<ws-url>` when not the default `ws://<host>:3000/rpc`), who is in, and Start for the host. Opening an invite link lands on the join screen with the code filled in. Empty seats show as "Open seat". Friends can join mid-race: they spectate and ride from the next restart. The create screen picks the race (Co-op, or Team race and then 👻 Ghost / 💥 Bump), the difficulty, then the course; the pickers (`radioPicker`, `racePicker`, `contactPicker`, `difficultyPicker`) live in `client/ui/pickers.ts`, shared with the start menu. A team room's screen shows Red and Blue columns (`n/MAX_TEAM`, a "Join Red"/"Join Blue" button each, disabled on your own team or a full one), the mode as text, or as the Ghost / Bump switch for the host, and Start disabled with `startBlocker`'s text while a team is empty. During a team race `showTeamPick` (same file) keeps a small strip at the bottom: a mid-race joiner sees "Ride next race for" with Red and Blue (`n/MAX_TEAM`, the full one disabled), a rider one button for the other team ("Next race: Blue ⇄"); both call `conn.setTeam`, which the server accepts mid-race and applies at the next Restart. The host's strip also has Ghost / Bump buttons (`conn.setMode`), the only way to change the mode once a race has started. A spectator's camera follows its team's raft, so picking a team also moves the view. A co-op room looks as before.
- **Team race client:** `FrameView` carries `raft` (the `Snapshot.crews` index `prev`/`curr` follow: the one you ride, else as a spectator your team's raft, else 0), `events` (your raft's plus `go`: felt by the HUD, audio, shake, rumble) and `rivalEvents` (every other raft's: only seen, as fart puffs and the rival riders' reactions; a Bump hit on your raft is already your own `bump` with `rival: true`). `Session.looks()` gives every raft's rider looks by raft index; `restart()` returns why it cannot (online, `startBlocker`), which the app shows as a brief banner. `crewsOf(view, raft)` is the inverse of `viewOf`. `client/render/rivals.ts` draws each other raft as a kit `raft` clone with its own rider animator and raft motion, ringed in its team color (`createTeamRing`, `client/teams.ts` `TEAM_COLORS`: Red, Blue); in Ghost every material is swapped for a cached see-through copy (opacity × 0.4, no depth write, no shadow; the kit shares materials with your raft), and a contact change on restart rebuilds it. The HUD (`drawTeams`) adds a marker per team on the progress bar (yours on top, both in team colors), a floating "Rival" tag in the rival's team color, and the result from `teamResult(crews, tick)` (`client/ui/result.ts`, tested): "<Team> wins!" in its color, or "Draw!", plus the gap to the runner-up (live while it races, fixed once it finishes) as a strip under the timer while your raft still races, then inside your finish card with both times and wipeouts. Spectators get the same.
- **Looks (cosmetic only, the sim never sees them):** every rider has a `Look` (`src/look.ts`): animal (capybara / hippo / croc / lobster), one of 12 `LOOK_COLORS` (the first 8 are the seat colors), a hat, an outfit and a gadget, plus one-click `COSTUMES` (police, nurse, doctor, firefighter, chef, pirate, …). The wardrobe dialog (`client/ui/wardrobe.ts`, with a turntable preview from `client/render/preview.ts`) opens from each human's seat in the start menu (name + look, saved as `fart-raft:players`), from the online name screen and from your seat in the room (player 1's look rides online). `Session.looks()` gives one look per rider on each raft; the race feeds your raft's to the HUD tags, the zone colors and `riders.ts`, which swaps a rider's rig when its look changes (kit riders stay hidden as templates; `cloneRig` copies the animal's and tints it). Hats, outfits and gadgets are built from Three primitives in `client/render/outfits.ts`, anchored per animal from `build_kit.py`'s rider numbers (no kit nodes). A new item is its name in `look.ts` (+ label) and a `case` in `outfits.ts`; a new animal is a builder in `build_kit.py` (a wardrobe-only `rider_N` after the four seat riders, `pnpm kit`) plus its `ANCHORS`, `KIT_RIDER` and `KIT_COLOR` entries in `outfits.ts`; the `Record` label tables and switch exhaustiveness catch a missing one.
- **Players:** the start menu (`client/ui/menu.ts`) picks humans (0–`MAX_LOCAL` = 4, one keyboard cluster each) whether bots fill empty seats, and the difficulty (Chill / Wild) and the race (Co-op, or a Ghost / Bump team race), both saved with the menu config; `?players=N&bots=0|1[&mode=wild][&race=ghost|bump]` skips it (`mode=` stays the difficulty, so old links keep working). A team race offline is your crew on raft 0 (Red) against `MAX_LOCAL` bots on raft 1 (Blue, pirates in the team color, `botCrewLook`), each bot reading `viewOf(snapshot, 1)`; the inputs go flat, yours first. Humans take the first seats (P1 WASD + Space, P2 Arrows + Enter/Right Shift, P3 IJKL + U/O, P4 Numpad 8456 + Numpad 0; a single human gets either cluster), bots the rest up to 4. Online rooms take up to 8 humans. Keys, pad stick and touch stick are all camera-relative.
- **App states** (`client/app.ts`): `menu`, `online` (name, create/join), `room` (seated, waiting for the first frame), `racing`. `go(next)` runs the current state's cleanups newest first, then enters the next; a generation counter makes async work that outlives its state (a menu promise, a loading session or scene) free what it made instead of entering. Esc and the touch ☰ go back to `menu` with `history.replaceState`, no reload. `racing` owns the held-key listener, R/Esc, touch controls, the session (`dispose()`: frees the Rapier world or closes the connection), the race (`dispose()`: WebGL context, GPU buffers, canvas, HUD and volume DOM) and the loop's `stop()`. One `AudioContext` lives for the app (browsers cap them): a race resumes it and suspends it on dispose.
- **Controls:** every human input (keyboard, gamepad, touch; local and online) is a plain `InputSource`: the stick or move keys slide the rider along its arc (camera-relative, `clampToZone`), and only the fart key/button farts (Space, Enter, the touch FART button, the pad's fart button; held, it fires again after `FART_COOLDOWN`). Nothing farts on its own: steering is walking to the right spot, then farting.
- **Bots** (`input/bot.ts`) are plain `InputSource`s that read their raft's latest `View`, nothing else, so the server can run them unchanged. Each slides to the spot in its arc opposite the push the crew needs and farts when its push lines up. Hazards move on a fixed schedule, so `input/crossing.ts` plans each crossing ahead: it follows candidate lanes and paces (steady, crawl, stop, back off, then full speed) as paths through time past the hazards' pure motion functions (`hazardBoxes` in `sim/hazards/index.ts`) and takes the one with the most room; the crew's bots share one plan. `bot.test.ts` races crews of 1–4, 6 and 8 on every course, in wild and in chill, headless and must finish with at most 3 wipeouts. Bot wipeout counts are knife-edge (a small tuning change flips a race from 0 to a death loop), so rerun it after touching `DIFFICULTY`.
- **Difficulty:** `createSim(level, [zones], { difficulty })`, `"chill"` (default) or `"wild"` (today's tuning, the one `bot.test.ts`'s ≤ 3 wipeouts bound is held to). All of it is one table, `DIFFICULTY` in `sim/constants.ts`: `hazardRate` (chill 0.7), `kindRates` (per-kind overrides: chill `spinner` and `cross` 0.5, since their only window is a launch timed against the bar), `respawnTicks`, `respawnBack`, `invulnerableTicks`, `walk`/`soloWalk` (ring walk speed multipliers, read through `walkSpeed(difficulty, crew)`). Read a rate only through `hazardRate(difficulty, kind)`. Hazard time is `hazardTime(difficulty, tick, kind)` in `sim/hazards/shape.ts`: the sim steps each hazard by `STEP * hazardRate(difficulty, kind)` (`Sim.hazardSteps`), and bots (`bot.ts`, `crossing.ts`, which also scales seconds ahead by the rate) and the renderer (`scene.ts`) read the difficulty from the snapshot, so never compute hazard time as `tick * STEP`. The lobby create screen and the start menu share the picker in `client/ui/pickers.ts`.
- **Feel knobs** live in `sim/constants.ts` (`FART_FORCE`, burst length/cooldown/cost, `WALK_SPEED`, damping, `CURRENT_SPEED`, gas regen). Tune on an empty pond before building courses.
- **Course JSON** is always loaded through `parseLevel()`, never cast. A new hazard kind is one module, `sim/hazards/<kind>.ts`, exporting a `HazardKind` (`create`: Rapier body, colliders and knock; `boxes`: what it fills at hazard time `t`; `reach`), plus its name in `HazardDef["kind"]`, an entry in `KINDS` (the validator's `HAZARD_KINDS` is derived from it) and a view in `VIEWS` in `client/render/hazards.ts` (and a kit node, or an `ASSET` alias). Both tables are `Record<HazardDef["kind"], …>`, so a missing entry fails the typecheck.
- **Channel courses:** a course is mostly one `channel` (centerline control points + `halfWidth` + spiked `spikes` spans by arc length). `sim/channel.ts` smooths it (Chaikin) and derives the bank colliders; terrain, bots, camera and the HUD progress bar all read the same samples. Edit `scripts/canyon.ts`, then `pnpm course`; gates and hazards are placed by arc length. The water flows downstream along the centerline at `CURRENT_SPEED` once the race starts (drag is relative to the water, `applyWaterDrag`), so an idle raft drifts; the water shader draws matching streaks from the ribbon's `aFlow` attribute. Hazards: `spinner` (bar spinning about its center; canyon's `spinner()` helper puts a 2.6 m half-length bar on a hub 1 m toward the bank it sweeps upstream, so the lane on the far bank, where the bar swings downstream with the raft, is open for over half of each half-turn: on a 14 m channel a centered bar closes every lane for ~70% of the turn whatever its length, because the 5.6 m hull meets the hub end), `sweeper` (bar hinged on a bank, swings `SWEEP_AMPLITUDE`), `log` (spiked log rolling across the channel: axis along `rot`, center runs `range` m either side of (x, y), `phase`), `bumper` (round spiked ball of radius `hx` that swells by `BUMPER_PULSE` and throws the raft harder, `BUMPER_KNOCK`), `cross` (two-bar spinner, for wide pools), `hammer` (mallet hinged on the bank `HAMMER_ARM` m back along `rot`, slams onto its smash zone once a cycle and only hurts while down), `piston` (spiked block resting in a bank, punches `range` m out along `rot`), `dropgate` (spiked bar of half-length `hx` along `rot`, bank to bank between two posts: every `period` s it shakes for `DROPGATE_SHAKE`, slams onto the water, rests `down` s and rises over `rise` s, defaults `DROPGATE_PERIOD`/`_DOWN`/`_RISE`; its collider exists only while `dropgateDown`, and the renderer fades the raised bar when it hides the raft), `doublegate` (two spiked doors hinged on the banks `hx` m either side of (x, y) along `rot`, each `hx` long: wide open they lie flat along their banks reaching upstream; every `period` s they swing shut over `DOUBLEGATE_CLOSE`, meet in the middle, stay shut `down` s and swing open over `rise` s, defaults `DOUBLEGATE_PERIOD`/`_SHUT`/`_OPEN`; open or shut, a door wipes the crew out, and the renderer fades the shut doors when they hide the raft) and `mine` (floating spiked mine of radius `hx`, still, or drifting `range` m either side of (x, y) along `rot` at `speed`; touching it wipes the crew out) and `mace` (spiked bob of radius `hx` hung from a gantry over (x, y), swinging like a pendulum `range` m either side along `rot` at `speed`, `MACE_SWING` rad from straight down; it rises on the arc (`maceBob`) and only hurts while lower than `MACE_HIT_LIFT`, through the middle of a swing, so it is pure timing; the renderer fades bob, rope and beam while they hide the raft; course helper `mace()` sets `range` = halfWidth − `MACE_BANK_GAP`). Motion lives in each kind's module as pure functions of time (`hammerLift` in `hammer.ts`, `pistonOut`, `dropgateLift`, `doublegateShut`, `mineCenter`, `maceBob`, …), shared by sim, bots and renderer; `index.ts` dispatches `hazardBoxes` / `hazardReach` by kind, and `shape.ts` keeps the shared bits (`hazardTime`, `cycle`, `smoothstep`, `span`, `NOWHERE`). `rapids` stretches on a channel run at `RAPIDS_SPEED` (`channel.ts` `flowSpeed`), and the water shader froths there. `ponds` (`{ from, to, halfWidth }` by arc length, wider than the channel, validated by `parseLevel`) open the channel into a round pool: the width eases out and back over `POND_RAMP` m (quarter sine) and everything reads it through `halfWidthAt(channel, s)` (bank colliders, tilted along the ramps; terrain; bot lanes; the START gate; course helpers that size hazards from the width), never `channel.halfWidth`. `sampleChannel` adds a sample every 1 m inside ponds. The water slows there to `CURRENT_SPEED` × halfWidth / `halfWidthAt` (same flow), and the shader's streaks fade out. A channel without `ponds` behaves exactly as before. Keep ponds on straights (the inner bank of a bend folds once the width nears the bend radius) and clear of hazards. A pond lengthens the course, so every hazard downstream meets the raft at a new point in its cycle: the canyon's ponds sit on stretched straights (48 m and 52 m added, control points after them shifted) whose lengths were picked by rerunning the bot races. The client adds lily pads off the racing line and shore boulders (`client/render/ponds.ts`); a rock-sized island (larger half-extent ≤ 1.5 m) is drawn as a grey boulder instead of a mesa. A thick wall (both half-extents ≥ `ISLAND_MIN_HALF`) is an island: an octagon in the sim and in the renderer (`sim/island.ts`). `scripts/course.ts` has the helpers `canyon.ts` and `graveyard.ts` share (`gate`, `dropgate`, `doublegate`, `mine`, …). A hazard spanning the whole channel leaves bots no lane, only timing: keep it on a calm run away from other hazards, and check the bot races, since a lone rider brakes slowly.
- **Boost pads** are not hazards: optional `LevelData.boosts` (plain `Box`es, validated by `parseLevel`, direction = `rot`), placed with the course helper `boost(s, lat)` (5 × 3 m, pointing downstream). While the raft's center is within `BOOST_REACH` of a pad, `sim/boost.ts` accelerates it along the pad at `BOOST_ACCEL` up to `BOOST_SPEED` (13 m/s vs ≈ 7 cruising); running onto one is a `boost` event (whoosh in `audio.ts`, spray in `wake.ts`, a little shake). The client draws red `>>` chevrons with a white rim that chase-blink and pop on a hit (`client/render/boosts.ts`). `crossing.ts` speeds its simulated crossing over pads, but a lone rider still brakes slowly: keep pads a good 30 m+ short of the next hazard's zone (canyon 266, 592, 872, 940; graveyard 122, 222, 465) and rerun the bot races after moving one.
- **Wipeouts, not lives:** any hazard or spike hit wipes the crew out (`hit` event, `Crew.deaths` counts them). The raft tumbles for `respawnTicks`, then reappears `respawnBack` m upstream of the last gate passed (`respawn` event), dead still, tanks full, with `invulnerableTicks` of grace (all per difficulty; wild = `RESPAWN_TICKS`, `RESPAWN_BACK`, `INVULNERABLE_TICKS`) the client blinks it for. The clock keeps running; the HUD shows a skull counter. The renderer and camera treat a jump over `TELEPORT` m as a cut (`coords.ts` `jumped`).
- **Volume:** `client/fx/volume.ts` holds master / farts / effects levels (pure rules + a store persisted as `fart-raft:volume`, mute as `fart-raft:muted`); `audio.ts` maps them onto the master gain and separate fart and effects buses. Master 0 counts as muted, and unmuting brings back the last audible level. Sliders (`client/ui/volume.ts`) sit in the start menu and behind the HUD speaker button; keys pressed inside them never reach the game's window key handlers, and Esc closes the popover instead of leaving the race.
- **Camera:** high chase camera like Fart Together (`chaseCamera.ts`: `BASE_FOV` 48, `BACK` 16, `HEIGHT` 12, `LOOK_AHEAD` 3.5, ≈37° down; `framing(aspect)` is the resting setup): at 1280x720 the raft is ≈15–20% of the width, a little below the middle, with ≈40 m of channel ahead. It faces the stream `HEADING_AHEAD` 16 m ahead of the raft, so it swings into bends early, never the raft's spin. FOV widens with speed (`SPEED_FOV` 6). Narrower than 16:9 widens the vertical FOV to keep the width (`fitWidth`, cap `MAX_FOV` 90). Portrait screens (`portraitness`: 0 at square or wider, 1 at aspect ≤ `PORTRAIT_FULL` 0.6) add up to `PORTRAIT_BACK` 4 / `PORTRAIT_HEIGHT` 7 / `PORTRAIT_LOOK_AHEAD` 9 m on top and raise the cap to `PORTRAIT_MAX_FOV` 105 (≈62° across on a phone), so the raft sits low with a long stretch of channel ahead; read every frame, so rotating the phone reframes live. Landscape is unchanged. Gate bars and signs fade to `FADED` 0.2 while they hide the raft (`gates.ts` `gateBlocksView`: a gate within `NEAR_GATE` of the raft, no more than `AHEAD` m beyond it, whose screen box overlaps the raft's; posts stay opaque), like the drop gate; checkpoint confetti fountains up and out from the sign's ends, not across the channel. Fart jets are short plumes of small translucent lime puffs pointing away from the rider, fading out within ~0.5 s (per-instance `aAlpha`, `fx/particles.ts`).
- **Sounds:** `client/fx/audio.ts` synthesizes everything except farts, which are CC0 Freesound clips in `public/sounds/fart-NN.mp3` (credits in `public/sounds/CREDITS.md`, bump `FART_CLIPS` when adding one). Each fart picks a random clip, pitched per seat (`seatRate`, any seat index) with ±10% jitter; the old synth fart plays until the clips decode.
- Tests: BDD nesting (`describe('given …')` → `describe('when …')` → `it('should …')`), and run the real `step()` rather than mocking Rapier.

## Blender pipeline (course export planned)

Blender MCP setup (done on this machine):

- Blender 5.2 (`brew install --cask blender`). The `blender_mcp.py` addon is in `~/Library/Application Support/Blender/5.2/scripts/addons/` and enabled in the saved user prefs.
- MCP registered at local scope for this project: `claude mcp add blender -e DISABLE_TELEMETRY=true -- uvx mcp-for-blender`.
- `pnpm blender` opens the project file and `start_mcp.py` starts the socket server, so no N-panel click is needed. Claude Code must start _after_ Blender to see the `mcp__blender__*` tools; restart the session if they're missing.

Rules for MCP sessions: save the `.blend` first (`execute_blender_code` runs arbitrary Python), and keep requests small ("add 5 rocks along the left bank", not "build the course") to avoid timeouts. Use `look` to check results visually.

A Python export script writes two files per course:

- `public/models/<course>.glb`: visual meshes (client only).
- `courses/<course>.json`: `LevelData` from naming conventions:
  - `col_*` → `walls` (box: position, rotation, half-extents)
  - `spawn_raft` → `spawn`
  - `checkpoint_NN` → `checkpoints` in order. The last one is the finish.
  - `hazard_<kind>_NN` with custom props (`speed`, …) → `hazards`

The server never parses `.glb`; it only needs the JSON.
